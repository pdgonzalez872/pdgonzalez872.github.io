testing-skip-factories
Testing in Elixirland (skip the factories)
Paulo Gonzalez
testing, elixir, ex_machina, llm

TL;DR: create test data through your contexts, not through factories. No insert(:user). Use the same function prod uses.

I've held this opinion for years. LLMs gave me a new reason to write it down.

The new reason: LLMs

The more the codebase shows an LLM that the context is the one place where actions on a resource happen, the better the code it generates. Fewer iterations, simpler code. 

# two ways to make a user. which one is real?
user = insert(:user, company: company)
{:ok, user} = Users.create_user(company, %{email: "paulo@acme.com"})

The LLM has to guess. Sometimes it guesses wrong.

  • - One path to create a thing. If tests create a company with Companies.create_company/1, the LLM sees that path everywhere and reuses it.
  • - ExMachina's insert skips the changeset. Test data can be in states prod data can never be in. The LLM learns from that data and writes code that assumes those states.
  • - The factory file is a second schema to keep in sync. When a test fails, the LLM "fixes" it by tweaking factory defaults instead of the code. Green test, wrong fix, another iteration.
  • - Tests that go through the context exercise the prod path. When generated code breaks a validation or a side effect, the test catches it on the first run, not in review.
  • - Less to load. The LLM reads the context module and knows how to make data. No factory file, no traits, no chained associations to trace.
The old reason: Factory Disease

I've called this Factory Hell before, but disease is a better description. It's silent. It doesn't hurt you immediately, which is exactly why people don't believe it's a problem. It bites 6 months later, and when it does, you can't revert it in a straightforward way.

It happens when factory creation gets chained. Someone adds an association to a factory because it's convenient for their feature. The next person copies that test. Now every test that builds one record builds ten.

At a company I used to work for, creating a Loan (the crux of the app) created a TON of objects. Here's how they dealt with it:

  • - 60 workers running in parallel on CircleCI. The suite took 20 minutes.
  • - A SimpleLoan factory, the least data necessary, not to be touched. Rolling it out took a big chunk of a senior engineer's time, mostly waiting on CI.
  • - A complex caching layer for tests. That was another senior engineer's full time job. It failed.
  • - Education. Usually forgotten when there was pressure to deliver.

I checked in with a friend still there: 20 minutes, now on 80 machines.

The cost isn't the machines. It's the engineer waiting 20 minutes, getting coffee, jumping into something else. Then morale, friction, and people leaving.

Why it spreads:

  • - Dev churn. People with tribal knowledge leave, new people come in.
  • - New devs haven't suffered it, so they don't see it.
  • - New devs copy the pattern in the last feature. Code review doesn't catch everything.
  • - Pressure to deliver fast.

It's not the stack. I've seen it in Ruby (factory_girl) and in Elixir (ExMachina, which brought the idea over). It's us.

Two code paths

With factories, the app has two code paths that you hope cross: application code (what happens in prod) and test code (what happens in tests). I've seen them not cross at both unicorns I've worked at. Neither had good test or demo environment data either. Frankensteins.

What to do instead

Use setup blocks and call the context. Only required fields (the changeset tells you what's required). If a test needs an association, create it in the test. 

setup do
  {:ok, company} = Companies.create_company(%{name: "Acme"})
  {:ok, user} = Users.create_user(company, %{email: "paulo@acme.com"})

  %{company: company, user: user}
end

Everything the test needs, in the test file.

When creating a thing touches more than one context, add a workflow layer where the contexts come together. I've seen codebases without it, and they coupled entity creation instead. 

defmodule MyApp.Workflows do
  alias MyApp.{Companies, Emails, Users}

  def register_company(company_name, user_email) do
    with {:ok, company} <- Companies.create_company(company_name),
         {:ok, user} <- Users.create_user(user_email),
         {:ok, _email} <- Emails.create_user_email(user) do
      {:ok, %{company: company, user: user}}
    else
      error ->
        # log, metrics
        error
    end
  end
end

One function for "register a company". Prod calls it. Tests call it. So does the LLM.

Tradeoffs

It's not free:

  • - You type more. Longer test files, some boilerplate.
  • - The same setup block shows up in many files.
  • - Some people find the tests too verbose.

What you get:

  • - Explicitness over convenience. Tests show intent.
  • - Failures are easier to diagnose, the data is right there.
  • - No "why is it so slow lately?" questions without answers.
  • - Flaky tests can be fixed without tribal knowledge.
  • - An LLM that gets it right on the first try more often.

The alternative is to keep silently trading convenience for performance.
