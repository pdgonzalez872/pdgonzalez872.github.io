TL;DR: one DigitalOcean droplet runs every small Phoenix app I have. Each app gets its own Linux user, Postgres database and port. Cloudflare serves the public HTTPS. Laptops reach the box only over Tailscale. No port is open to the internet.

The shape

Here is what we are going to build: 

 browser ──https──> Cloudflare (DNS, TLS, WAF)
                         │  tunnel, dialed out by the box
                         ▼
 ┌──────────────── droplet "box" (Ubuntu 26.04) ──────────────────┐
 │ cloudflared ──> 127.0.0.1:4001  app@my_app     (user my_app)   │
 │             ──> 127.0.0.1:4002  app@other_app  (user other_app)│
 │                       │                                        │
 │                 Postgres 127.0.0.1:5432                        │
 │                 one database + one role per app                │
 │                                                                │
 │ sshd :22 ── reachable only on tailscale0 ──┐                   │
 └────────────────────────────────────────────┼───────────────────┘
                                              │ Tailscale (WireGuard)
                    laptops: ssh deploy@box deploy my_app

The box only makes outbound connections (Cloudflare, Tailscale, apt, GitHub, Hex).

The tools

These are the tools we use, and what each one does for us:

  • - DigitalOcean: the machine, a firewall in front of it, a browser Recovery Console, weekly backups, alerts.
  • - Namecheap: where I bought the domains. Its nameservers point to Cloudflare.
  • - Cloudflare: handles traffic -> answers DNS, serves HTTPS and filters junk traffic. cloudflared on the box dials out to Cloudflare and keeps the connection open, and requests come back down that connection, so the box doesn't need an open port.
  • - Tailscale: a private network between the laptops and the box, on WireGuard. SSH is only reachable through it.
  • - GitHub: stores code, nothing else (no Actions, no Releases).
  • - systemd: starts every app, restarts it if it crashes, caps its memory and sandboxes it. One template unit runs all of them.
  • - mise: installs the Erlang/Elixir versions each repo pins. Only the build users use it.
Decisions (and why)
  • - Cloudflare Tunnel instead of nginx and open 80/443. Nothing listens on the public interface, so it doesn't matter if the origin IP leaks. LiveView works through it, and it's free.
  • - Tailscale for SSH instead of public 22 and fail2ban. With no public ports, fail2ban has nothing to watch, so I dropped it.
  • - Build on the box. Building on the box avoids "works on my laptop" problems, and a laptop only needs SSH. Deploys build whatever is pushed to GitHub.

The droplet is a 2 vCPU / 4 GB AMD, $28/mo, about $34 with weekly backups. Cloudflare and Tailscale are free.

So, let's get started!
Step 1: Accounts (the biggest security hole)

Whoever controls the DO account has root on the box. Whoever controls Cloudflare or Namecheap controls where the domain points. Losing one of these accounts is the most likely way to lose the box. So, before we create anything, let's lock the accounts down:

  • - 2FA with a hardware key or a TOTP app (no SMS) on DigitalOcean, Cloudflare, Namecheap, GitHub, and whatever you log into Tailscale with.
  • - Buy the domain(s). The registrar lock turns on automatically if you buy them through Namecheap.
  • - The admin's sudo password in a password manager. It's also the Recovery Console login in DO.

Security checkpoint: nobody gets to the box, the DNS or the code with a password alone.

Step 2: Create the droplet (Digital Ocean - DO)

Let's start on the laptop and create the SSH key we'll use for the box: 

#
# we are in the laptop
#

# ssh-keygen -t: the key type
# ssh-keygen -f: the key file
# ssh-keygen -C: a comment naming the laptop
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_box -C "me-thinkpad-2026"     # passphrase
cat ~/.ssh/id_ed25519_box.pub

Now go to DO -> Create Droplet and choose the following:

  • - Ubuntu 26.04 LTS, which gets security patches until 2031.
  • - Authentication: SSH key. Paste the .pub from above. This also turns off password SSH, same as in 2021.
  • - Tick Monitoring and Backups.
  • - Networking -> Firewalls -> new firewall. Inbound: SSH 22 from your IP only. This gets removed in step 4.

Security checkpoint: same as in 2021. DO only lets us in through SSH, as root, with the key we just created. Logging in with a password is disabled.

Step 3: First login, admin user, start hardening

Let's log in as root and create a user that is not root. We add it to the sudo group, so it needs its password every time it runs a privileged command, and we give it the same SSH key. Let's call this new user admin. We also update the machine and install a few packages we'll need later. 

#
# we are in the laptop
#

# ssh -i: use this private key
ssh -i ~/.ssh/id_ed25519_box root@PUBLIC_IP

#
# we are in the box, as root
#

adduser admin                     # strong password, into the password manager
# usermod -a: append to the groups instead of replacing them
# usermod -G: the supplementary group to add (sudo)
usermod -aG sudo admin
# install -d: create directories instead of copying a file
# install -m: set the permission mode
# install -o: set the owner
# install -g: set the group
install -d -m 700 -o admin -g admin /home/admin/.ssh
cp /root/.ssh/authorized_keys /home/admin/.ssh/ && chown admin:admin /home/admin/.ssh/authorized_keys

# apt -y: answer yes to every prompt
apt update && apt -y full-upgrade
apt -y install ufw curl git jq build-essential autoconf m4 libncurses-dev libssl-dev vim
# remove root services a server doesn't use. Any local user can talk to them,
# so a bug in one of them is a way to root that skips our sandbox.
apt -y purge snapd modemmanager udisks2 packagekit fwupd bolt multipath-tools open-iscsi && apt -y autoremove --purge
timedatectl set-timezone UTC

Now let's configure SSH. Ubuntu reads sshd_config.d/*.conf in order and the first value wins, so our 00- file beats DO's 50-cloud-init.conf: 

#
# we are in the box, as root
#

cat > /etc/ssh/sshd_config.d/00-box.conf <<'EOF'
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
AuthenticationMethods publickey
AllowGroups sudo deploy
X11Forwarding no
AllowAgentForwarding no
MaxAuthTries 3
LoginGraceTime 20
EOF
# sshd -t: test the config and exit; restart only if it passes
sshd -t && systemctl restart ssh

Keep the root session open and test ssh -i ~/.ssh/id_ed25519_box admin@PUBLIC_IP and sudo -v in a second terminal.

After step 4, the public IP stops answering on 22, and we log in with ssh box.

From here on we work as admin. Let's add swap, hide each user's processes from the others, leave cron to root only, cap the logs and set up automatic updates: 

#
# we are in the box, as admin: ssh -i ~/.ssh/id_ed25519_box admin@PUBLIC_IP
#

# swap: headroom for builds
# fallocate -l: the size of the file to allocate
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
# tee -a: append to the file instead of overwriting it
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

# hide every user's processes from the others. /proc/*/cmdline is
# world-readable by default, and a command line can carry secrets.
echo 'proc /proc proc defaults,nosuid,nodev,noexec,hidepid=invisible 0 0' | sudo tee -a /etc/fstab
# mount -o: mount options; remount applies them to the mounted /proc
sudo mount -o remount,nosuid,nodev,noexec,hidepid=invisible /proc

# only root gets a crontab, so app and build users can't schedule anything
echo root | sudo tee /etc/cron.allow

# cap the logs
# mkdir -p: create parent directories, no error if it exists
sudo mkdir -p /etc/systemd/journald.conf.d
printf '[Journal]\nSystemMaxUse=1G\n' | sudo tee /etc/systemd/journald.conf.d/size.conf
sudo systemctl restart systemd-journald

# unattended-upgrades is on by default; let it reboot at 09:00 UTC
sudo tee /etc/apt/apt.conf.d/52box <<'EOF'
Unattended-Upgrade::Automatic-Reboot "true";
Unattended-Upgrade::Automatic-Reboot-Time "09:00";

// Third-party repos are skipped unless listed. Tailscale and cloudflared
// (steps 4 and 12) get patched like the OS.
// Names come from: apt-cache policy | grep -o 'o=[^,]*' | sort -u
Unattended-Upgrade::Origins-Pattern {
  "origin=Tailscale";
  "origin=cloudflared";
};

// The tailscale package restarts tailscaled itself. cloudflared's does not,
// so restart it when the running binary has been replaced:
// /proc/PID/exe then ends in "(deleted)".
DPkg::Post-Invoke { "readlink /proc/$(systemctl show -p MainPID --value cloudflared)/exe 2>/dev/null | grep -q deleted && systemctl restart cloudflared || true"; };
EOF

Security checkpoint: Big change, same as last time. We can no longer log in as root at all, and passwords don't work over SSH. We can still do whatever we want as admin, but we need to know its password to use sudo. The box also patches itself and reboots when it needs to.

Step 4: Tailscale, then close port 22

Let's start in the Tailscale admin console, because the tag we give the box has to exist before the box can use it. Turn on MagicDNS (so box resolves) and replace the default allow-all ACL. The default lets the box reach your laptops. This one only lets laptops reach the box on port 22: 

{
  "tagOwners": { "tag:box": ["autogroup:admin"] },
  "grants": [
    { "src": ["autogroup:member"], "dst": ["tag:box"], "ip": ["tcp:22"] }
  ]
}

Now let's install Tailscale on the box and bring it up with that tag: 

#
# we are in the box, as admin, still over the public IP
#

# curl -f: fail on HTTP errors instead of saving the error page
# curl -s: silent, no progress bar
# curl -S: still show errors when silent
# curl -L: follow redirects
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up --advertise-tags=tag:box --hostname=box

Back in the admin console, disable key expiry on the box. Then install Tailscale on the laptop and tell SSH which key and user to use for the box: 

#
# we are in the laptop
#

# curl -f: fail on HTTP errors instead of saving the error page
# curl -s: silent, no progress bar
# curl -S: still show errors when silent
# curl -L: follow redirects
curl -fsSL https://tailscale.com/install.sh | sh && sudo tailscale up
printf 'Host box\n  HostName box\n  User admin\n  IdentityFile ~/.ssh/id_ed25519_box\n  IdentitiesOnly yes\n  AddKeysToAgent yes\n' >> ~/.ssh/config
ssh box     # logs in as admin, over Tailscale

Once that works, let's close the port: 

#
# we are in the box, as admin, now over Tailscale: ssh box
#

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow in on tailscale0 to any port 22 proto tcp
sudo ufw enable

Then delete the SSH rule from the DO firewall, which leaves it with no inbound rules. 

 internet ──X──> DO Cloud Firewall    no inbound rules
 internet ──X──> ufw on the box       deny incoming

 laptop ──Tailscale──> tailscale0 ──> sshd :22     the only way in

 box ──outbound──> Cloudflare, Tailscale, apt, GitHub, Hex

And you can verify things worked by running:

# we are in the laptop, with Tailscale off
#

# nc -v: verbose, print whether the connection worked
# nc -z: only check if the port is open, send no data

nc -vz -w 5 PUBLIC_IP 22

If Tailscale ever breaks, the way back in is DO -> droplet -> Access -> Recovery Console, a terminal in the browser that doesn't go over the network.

Security checkpoint: in 2021, the only ports accessible to the external world were 22, 80 and 443. Now there are none, and two firewalls enforce it: DO's outside the box and ufw inside.

Step 5: Postgres, local only

Ubuntu 26.04 ships Postgres 18, so there's no extra repo, and it gets patched with the rest of the OS. The defaults are already what I want: localhost only, scram-sha-256, peer auth for postgres. Let's install it, add some tuning for a small box and close the default database to everyone: 

#
# we are in the box, as admin: ssh box
#

# apt -y: answer yes to every prompt
sudo apt -y install postgresql
sudo tee /etc/postgresql/18/main/conf.d/box.conf <<'EOF'
shared_buffers = 256MB
effective_cache_size = 1GB
work_mem = 8MB
maintenance_work_mem = 64MB
max_connections = 100
EOF
sudo systemctl restart postgresql
# sudo -u: run the command as this user
# psql -c: run this one SQL command and exit
cd /tmp && sudo -u postgres psql -c "REVOKE CONNECT ON DATABASE postgres FROM PUBLIC;"
# ss -t: TCP sockets
# ss -l: listening sockets only
# ss -n: numeric addresses and ports, no name lookups
# ss -p: show the process that owns each socket
ss -tlnp | grep 5432          # 127.0.0.1 / ::1 only

Security checkpoint: the superuser has no password and only works through sudo -u postgres, which fixes the postgres/postgres password from 2021.

Step 6: The deploy user

Every laptop logs in as one user, deploy, with its own key. Every key gets a forced command, so the only program that ever runs is deploy-gate, whatever the laptop asks for. Let's create that user, the directories the scripts will use, and the only sudo rule it gets: 

#
# we are in the box, as admin: ssh box
#

# GitHub's host key, system-wide and root-owned, so no build can swap it
# ssh-keyscan -t: the key type to fetch
ssh-keyscan -t ed25519 github.com | sudo tee /etc/ssh/ssh_known_hosts
# ssh-keygen -l: show the key's fingerprint
# ssh-keygen -f: the key file
ssh-keygen -lf /etc/ssh/ssh_known_hosts    # compare with GitHub's published fingerprint

sudo useradd --create-home --shell /bin/bash --groups systemd-journal deploy
# install -d: create directories instead of copying a file
# install -m: set the permission mode
# install -o: set the owner
# install -g: set the group
sudo install -d -m 750 -o root -g deploy /home/deploy/.ssh
sudo install -m 640 -o root -g deploy /dev/null /home/deploy/.ssh/authorized_keys
# root owns everything in deploy's home, so the deploy user can't swap .ssh or edit .bashrc
# chown -R: apply to the directory and everything inside it
# chmod -R: apply to the directory and everything inside it
sudo chown -R root:deploy /home/deploy
sudo chmod -R g-w,o-rwx /home/deploy

sudo install -d -m 751 /etc/apps /srv/apps
sudo install -d -m 755 -o root -g root /srv/build

echo 'deploy ALL=(root) NOPASSWD: /usr/local/bin/deploy-app, /usr/local/bin/pgdump-app' | sudo tee /etc/sudoers.d/deploy
# visudo -c: check the sudoers files for errors, change nothing
sudo chmod 440 /etc/sudoers.d/deploy && sudo visudo -c

Everything in deploy's home is owned by root, so even a shell as deploy couldn't add a key or change what runs at login.

A line in authorized_keys looks like this: 

restrict,command="/usr/local/bin/deploy-gate" ssh-ed25519 AAAA... my-laptop-2026
restrict,command="/usr/local/bin/deploy-gate 'my_app,game_*'" ssh-ed25519 AAAA... a-friends-laptop-2026

One line per laptop. restrict turns off forwarding and the PTY, and the argument to deploy-gate limits a key to those apps, and to deploying main.

Security checkpoint: a laptop key can run exactly one program on the box, deploy-gate, and the deploy user can use sudo for exactly two scripts.

I install mise from its apt repo so it gets updates. Each repo pins Erlang/Elixir in mise.toml, and each app's build user installs its own copy. All of these files are in this gist, with a README that maps each one to its path in the repo and on the box.

install.sh validates first (visudo -c, bash -n on every script), copies only what changed, reloads ssh and systemd, and prints any disruptive restarts for me to run. If a new sshd config fails sshd -t, it puts the old one back, since a broken sshd config would lock me out. (This was a mindblow here, thanks AI). 

#!/usr/bin/env bash
#
# file on the laptop: ~/dev/box/install.sh
# runs on the box: boxsync copies it to ~/box/install.sh and runs it with sudo
#

# install.sh   run on the box: sudo ~/box/install.sh
#
# Everything under root/ mirrors its real path on the box and is copied there,
# root-owned: root/etc/ssh/sshd_config.d/00-box.conf -> /etc/ssh/sshd_config.d/00-box.conf
# Only files that differ are copied, and only the services they belong to are
# touched. Files removed from the repo are NOT removed from the box; delete those by hand.
set -euo pipefail
[[ $EUID -eq 0 ]] || { echo "run with sudo" >&2; exit 1; }
cd "$(dirname "$0")/root"

# 1. validate before touching anything: a broken sudoers file or script must never land
visudo -c -f etc/sudoers.d/deploy >/dev/null
for f in usr/local/bin/* usr/local/lib/box/*; do bash -n "$f"; done

# 2. copy what changed. Scripts 0755, sudoers 0440, everything else 0644.
changed=()
while read -r f; do
  dest=/${f#./}
  case $dest in
    /usr/local/bin/*) mode=0755 ;;
    /etc/sudoers.d/*) mode=0440 ;;
    *)                mode=0644 ;;
  esac
  cmp -s "$f" "$dest" 2>/dev/null && continue
  # keep the old sshd drop-in so a bad one can be put back (a broken sshd config is a lockout)
  [[ $dest == /etc/ssh/* && -f $dest ]] && cp -p "$dest" "$dest.prev"
  install -D -m "$mode" -o root -g root "$f" "$dest"
  changed+=("$dest")
  echo "updated $dest"
done < <(find . -type f | sort)

[[ ${#changed[@]} -eq 0 ]] && { echo "nothing changed"; exit 0; }
changed_any() { local p; for p in "${changed[@]}"; do [[ $p == $1 ]] && return 0; done; return 1; }

# 3. apply. Safe reloads happen now; disruptive restarts are only suggested.
if changed_any '/etc/ssh/*'; then
  if sshd -t; then
    systemctl reload ssh && echo "ssh reloaded"
  else
    for p in "${changed[@]}"; do [[ $p == /etc/ssh/* && -f $p.prev ]] && mv "$p.prev" "$p"; done
    echo "sshd config invalid: previous version restored, ssh NOT reloaded" >&2
    exit 1
  fi
fi
rm -f /etc/ssh/sshd_config.d/*.prev
if changed_any '/etc/systemd/system/*'; then systemctl daemon-reload && echo "systemd reloaded"; fi
if changed_any '/etc/systemd/journald.conf.d/*'; then systemctl restart systemd-journald && echo "journald restarted"; fi
if changed_any '/etc/postgresql/*'; then echo "postgres config changed: sudo systemctl restart postgresql (brief app DB blip)"; fi
if changed_any '/etc/systemd/system/app@.service'; then echo "app unit changed: restart apps to apply: sudo systemctl restart 'app@*'"; fi
if changed_any '/etc/systemd/system/cloudflared.service'; then echo "tunnel unit changed: sudo systemctl enable --now cloudflared (or restart; a few seconds of downtime)"; fi
echo "done"

And this is the function we use on an admin laptop to sync it: 

#
# file on the laptop: ~/.bashrc (a laptop with admin)
# runs on the laptop: type boxsync after every push to ~/dev/box
#

boxsync() {
  # stop unless the clone is a clean copy of origin/main
  git -C ~/dev/box fetch -q || return 1
  if [[ -n $(git -C ~/dev/box status --porcelain) || $(git -C ~/dev/box rev-parse HEAD) != $(git -C ~/dev/box rev-parse origin/main) ]]; then
    echo "~/dev/box is not a clean copy of origin/main: commit + push, or pull, first" >&2
    return 1
  fi
  # rsync -a: archive: recursive, keeps permissions, times and symlinks
  # ssh -t: give the session a terminal (sudo needs one to ask for the password)
  rsync -a --delete ~/dev/box/ box:box/ && ssh -t box sudo box/install.sh
}

--delete makes the box match your local copy, so a stale clone would put old scripts back. The check makes that impossible to do by accident.

From here on, the config files from steps 3-6 come from this repo. Edit them here, not on the box, or the next sync overwrites them. The scripts and units in that tree are in the steps that follow (and app-console and add-deploy-key are further down). Put them all in the repo and sync once before running new-app, which needs them on the box.

Step 9: new-app

Now let's add an app. new-app runs once per app. Each app is named after its OTP app name, and that name is the Linux user, the database, the role, the systemd instance and the release. It runs on the box, not on the laptop: boxsync already put it in /usr/local/bin there. Log in as admin over Tailscale, with the Host box entry from step 4: 

#
# we are in the laptop
#

ssh box     # admin, over Tailscale (step 4)

#
# we are in the box, as admin
#

sudo new-app my_app 4001 myapp.example.com git@github.com:owner/my_app.git

 sudo new-app my_app 4001 myapp.example.com git@github.com:owner/my_app.git
   │
   ├─ user my_app           can't log in, owns none of its code
   ├─ user b_my_app         builds this app only, home /srv/build/my_app
   ├─ db + role my_app      random password, nobody else can connect
   ├─ /etc/apps/my_app.env  secrets generated here, never on a laptop
   ├─ GitHub deploy key     read-only, this repo only
   └─ app@my_app            enabled

#!/usr/bin/env bash
#
# file on the laptop: ~/dev/box/root/usr/local/bin/new-app
# runs on the box: boxsync installs it as /usr/local/bin/new-app
#

# new-app APP PORT HOST GIT_SSH_URL
#   sudo new-app my_app 4001 myapp.com git@github.com:OWNER/my_app.git
# Creates the Linux user, build user, database, role, secrets, deploy key and systemd instance.
set -euo pipefail
app=$1 port=$2 host=$3 repo=$4
# max 30 chars so the build user "b_APP" fits Linux's 32-char user names
[[ $app =~ ^[a-z][a-z0-9_]{1,29}$ ]] || { echo "app must be the OTP app name, ^[a-z][a-z0-9_]+$, max 30 chars" >&2; exit 2; }
[[ $port =~ ^4[0-9]{3}$ ]] || { echo "port must be 4000-4999" >&2; exit 2; }
[[ $repo == git@github.com:* ]] || { echo "use the ssh url git@github.com:owner/repo.git" >&2; exit 2; }
[[ -e /etc/apps/$app.env ]] && { echo "$app already exists" >&2; exit 1; }
if grep -qx "PORT=$port" /etc/apps/*.env 2>/dev/null; then echo "port $port is taken" >&2; exit 1; fi
cd /tmp

# 1. a user that can't log in and owns none of its code
useradd --system --user-group --no-create-home --home-dir /nonexistent --shell /usr/sbin/nologin "$app"
install -d -o root -g "$app" -m 0750 "/srv/apps/$app" "/srv/apps/$app/releases"

# 1b. a build user just for this app: its home holds its checkout, toolchain,
#     caches and deploy key, and nothing of any other app's
b=b_$app
useradd --system --user-group --no-create-home --home-dir "/srv/build/$app" --shell /usr/sbin/nologin "$b"
install -d -o "$b" -g "$b" -m 0700 "/srv/build/$app" "/srv/build/$app/.ssh"

Step 10: Deploys

Who can do what, from a laptop key down to the running app: 

 laptop key
   │  ssh deploy@box deploy my_app
   ▼
 deploy ── forced command: deploy-gate. no shell, no forwarding
   │  sudo, exactly two scripts
   ▼
 deploy-app (root)
   ├──> build-app as b_my_app     throwaway sandboxed unit, sees no secrets
   │    root validates what it built, installs it root-owned
   ├──> bin/migrate as my_app     same sandbox as the app
   ▼
 app@my_app (user my_app)         reads its code, writes only /var/lib/my_app

deploy-gate is the forced command, so these five verbs are all a laptop can run: 

#!/usr/bin/env bash
#
# file on the laptop: ~/dev/box/root/usr/local/bin/deploy-gate
# runs on the box: boxsync installs it as /usr/local/bin/deploy-gate
#

# deploy-gate [app1,app2,...]   the deploy user can do exactly these things and nothing else
set -euo pipefail
allowed=${1:-*}
read -r verb app arg _ <<< "${SSH_ORIGINAL_COMMAND:-help}"
logger -t deploy-gate "from=${SSH_CONNECTION%% *} allowed=$allowed cmd=${SSH_ORIGINAL_COMMAND:-}"
known() {
  [[ ${app:-} =~ ^[a-z][a-z0-9_]{1,30}$ && -f /etc/apps/$app.env ]] || { echo "unknown app: ${app:-}" >&2; exit 2; }
  local p; IFS=, read -ra pats <<< "$allowed"
  for p in "${pats[@]}"; do [[ $app == $p ]] && return 0; done   # unquoted $p: glob match
  echo "this key can't touch $app" >&2; exit 2
}
case $verb in
  # a build runs the repo's code as b_APP and can leave things behind for the
  # next build, so only admin keys (no argument) may build something other than main
  deploy)   known; [[ $# -eq 0 || ${arg:-main} == main ]] || { echo "this key can only deploy main" >&2; exit 2; }
            exec sudo /usr/local/bin/deploy-app "$app" "${arg:-main}" ;;
  rollback) known; exec sudo /usr/local/bin/deploy-app --rollback "$app" ;;
  dump)     known; [[ $# -eq 0 ]] || { echo "this key can't dump databases" >&2; exit 2; }
            exec sudo /usr/local/bin/pgdump-app "$app" ;;
  logs)     known; n=${arg:-200}; [[ $n =~ ^[0-9]{1,5}$ ]] || exit 2
            exec journalctl -u "app@$app" -n "$n" --no-pager ;;
  status)   exec systemctl list-units 'app@*' --all --no-pager ;;
  *)        echo "usage: deploy APP [ref] | rollback APP | dump APP | logs APP [n] | status" >&2; exit 2 ;;
esac

from= is the laptop's Tailscale IP, which is how I know who deployed.

What a deploy does: 

 ssh deploy@box deploy my_app main
  │
  ├─ 1. build      as b_my_app, in a throwaway sandboxed unit
  ├─ 2. validate   root checks rel/LATEST and the release dir
  ├─ 3. install    /srv/apps/my_app/releases/SHA, root-owned
  ├─ 4. migrate    bin/migrate as my_app ── fails? old release keeps running
  ├─ 5. switch     current -> SHA, previous -> old
  ├─ 6. restart    systemctl restart app@my_app
  └─ 7. GET /      ok:   "deployed my_app SHA"
                   fail: switch back, restart the old one, exit 1

#!/usr/bin/env bash
#
# file on the laptop: ~/dev/box/root/usr/local/bin/deploy-app
# runs on the box: boxsync installs it as /usr/local/bin/deploy-app
#

# deploy-app APP [ref]          build, migrate, switch, restart, health check, auto-rollback
# deploy-app --rollback APP     switch back to the previous release (does NOT undo migrations)
set -euo pipefail
source /usr/local/lib/box/sandbox.sh
if [[ ${1:-} == --rollback ]]; then mode=rollback app=${2:-}; else mode=deploy app=${1:-} ref=${2:-main}; fi
[[ $app =~ ^[a-z][a-z0-9_]{1,30}$ && -f /etc/apps/$app.env ]] || { echo "unknown app: $app" >&2; exit 2; }

root=/srv/apps/$app
port=$(sed -n 's/^PORT=//p' "/etc/apps/$app.env")
exec 9>"/run/lock/deploy-$app.lock"
flock -n 9 || { echo "a deploy of $app is already running" >&2; exit 1; }

switch_to() { ln -sfn "$1" "$root/current.tmp" && mv -T "$root/current.tmp" "$root/current"; }
healthy() { curl -fsS -o /dev/null --max-time 5 --retry 20 --retry-delay 2 --retry-all-errors "http://127.0.0.1:$port/"; }
# migrations run the new, untested release: same sandbox as app@.service
as_app() { app_sandbox "$app"; systemd-run --quiet --wait --pipe --collect "${SANDBOX[@]}" "$@"; }

if [[ $mode == rollback ]]; then
  prev=$(readlink -e "$root/previous") || { echo "no previous release" >&2; exit 1; }
  cur=$(readlink -e "$root/current")
  switch_to "$prev" && ln -sfn "$cur" "$root/previous"
  systemctl restart "app@$app"
  healthy && echo "rolled back $app to $(basename "$prev")"
  exit
fi

[[ $ref =~ ^[A-Za-z0-9][A-Za-z0-9._/-]{0,99}$ ]] || { echo "bad ref: $ref" >&2; exit 2; }
logger -t deploy "start $app ref=$ref by ${SUDO_USER:-root}"

# 1. build as this app's own build user, in a throwaway sandboxed unit with a clean
#    environment. When the unit ends, systemd kills everything in it, so no
#    background process from the build is still running during the steps below.
b=b_$app
id "$b" >/dev/null 2>&1 || { echo "no build user $b" >&2; exit 1; }
systemd-run --quiet --wait --pipe --collect --unit="build-$app-$$" \
  --uid="$b" --gid="$b" \
  -p NoNewPrivileges=yes -p ProtectSystem=strict -p ProtectHome=yes -p PrivateTmp=yes \
  -p PrivateDevices=yes -p ProtectProc=invisible -p ReadWritePaths="/srv/build/$app" \
  -p IPAddressDeny=169.254.169.254 -p MemoryMax=2G -p RuntimeMaxSec=3600 \
  -E HOME="/srv/build/$app" -E PATH=/usr/local/bin:/usr/bin:/bin -E LANG=C.UTF-8 \
  /usr/local/bin/build-app "$app" "$ref" >&2

# 2. LATEST and rel/ were written by build code: validate before root touches them.
#    Never echo LATEST's content (it could be a symlink to a root-only file).
sha=$(head -c 64 "/srv/build/$app/rel/LATEST")
[[ $sha =~ ^[0-9a-f]{12}$ ]] || { echo "bad sha in LATEST" >&2; exit 1; }
built=/srv/build/$app/rel/$sha
[[ -d $built && $(realpath -e "$built") == "$built" ]] || { echo "bad release dir" >&2; exit 1; }

# 3. install: root owns the code, the app can only read it
new=$root/releases/$sha
rm -rf "$new"
cp -a "$built" "$new"
chown -R root:"$app" "$new"
chmod -R u+rwX,g+rX,g-w,o-rwx "$new"

# 4. migrate with the new code before switching; if this fails the old release keeps running
as_app "$new/bin/migrate"

# 5. switch, restart, verify
old=$(readlink -e "$root/current" || true)
switch_to "$new"
if [[ -n $old && $old != "$new" ]]; then ln -sfn "$old" "$root/previous"; fi
systemctl restart "app@$app"
if ! healthy; then
  echo "health check failed on :$port, rolling back" >&2
  if [[ -n $old ]]; then switch_to "$old"; systemctl restart "app@$app"; fi
  logger -t deploy "FAILED $app $sha"
  exit 1
fi
logger -t deploy "ok $app $sha"
echo "deployed $app $sha"

# 6. keep the five newest releases
ls -1dt "$root"/releases/*/ | tail -n +6 | xargs -r rm -rf

Rollback doesn't undo migrations, so I back up the database with ssh deploy@box dump my_app before risky ones.

Step 12: Cloudflare Tunnel

Don't run cloudflared service install TOKEN. It puts the token in your shell history and in a unit file every local user can read, apps included. With a stolen token, someone can run their own connector and receive some of your traffic.

  • 1. Zero Trust -> Networks -> Tunnels -> Create tunnel, name it box. Copy the token and skip the install command it shows.
  • 2. Install just the package from Cloudflare's apt repo.
  • 3. Token into a root-only file, typed in an editor so it never hits shell history.
  • 4. The unit (from the box repo) hands the file to the service with LoadCredential= and runs cloudflared tunnel run --token-file as a sandboxed DynamicUser.

Step 13: Domains and subdomains

Each domain is one Cloudflare zone, which we set up once. Each hostname, apex or subdomain, is one tunnel route to one app's port: 

 Namecheap ──nameservers──> Cloudflare zone example.com
                                  │
                   tunnel "box", one route per hostname
                                  │
   example.com         ──> 127.0.0.1:4001   main_site
   app.example.com     ──> 127.0.0.1:4002   tracker
   admin.example.com   ──> 127.0.0.1:4003   back_office  (+ Cloudflare Access)
   www.example.com     ──> 301 to the apex  (a Cloudflare rule, not an app)

Once per domain:

  • 1. Buy it.
  • 2. Cloudflare -> Add a site -> Free. A new domain has no records, so there's nothing to import. If the domain already had DNS somewhere, especially email (MX, SPF/DKIM), check that Cloudflare imported those records: after step 3, Cloudflare is the only one answering for the domain.
  • 3. Namecheap -> Nameservers -> Custom DNS -> Cloudflare's two. Cloudflare assigns them per site, so copy them from the new site's page.
  • 4. SSL/TLS: pick Full (strict) explicitly, turn on Always Use HTTPS, and set the minimum TLS to 1.2.
  • 5. www -> apex: a proxied AAAA www 100:: placeholder, plus the "Redirect from WWW to root" rule. Ignore the warning that www isn't proxied.

Once per hostname: new-app on the box (Step 9), then in Cloudflare Tunnels -> box -> add a route to http://127.0.0.1:PORT, then deploy from the laptop (Step 10).

  • - Keep subdomains one level deep. The free certificate covers *.example.com but not a.b.example.com.
  • - Use 127.0.0.1 in routes. localhost can resolve to ::1, and the apps only listen on IPv4.
  • - Private apps get Cloudflare Access. From inside the box, any other app can curl 127.0.0.1:PORT and skip it, so the app checks the Access JWT too.
Step 14: What each Phoenix repo needs

Each Phoenix repo needs a few things before its first deploy:

  • - mix phx.gen.release committed. The scripts call bin/server and bin/migrate.
  • - mise.toml pins Erlang and Elixir (Node only if npm deps exist), nothing else, because the build runs mise install on the box, hooks included.
  • - Bind to loopback, allow the real origin (below).
  • - Set force_ssl (below). The tunnel reaches the app over plain HTTP, so without it Plug never sees https: the session cookie goes out without Secure and there is no HSTS header.
  • - Anything that writes to disk writes under /var/lib/my_app, the only writable dir. tzdata's auto-update is the common case.
  • - GET / is cheap, since the health check calls it.
  • - Nothing trusts localhost or remote_ip, because through the tunnel every request comes from 127.0.0.1. CF-Connecting-IP is OK for rate limits and logs, but not for auth, since other apps on the box can send it too.
  • - No System.get_env("MIX_ENV") at runtime, because nothing sets it in a release. Use config_env() instead.
  • - If the app runs jobs or timers on its own (Oban, Quantum, a GenServer on a timer), turn them off when BOX_CONSOLE is set (below). A console is a second copy of the app, and it shouldn't run the jobs too.

From an admin laptop, install the .pub with add-deploy-key. --admin is for your own laptops: deploys, database dumps and a shell as admin. --apps is for anyone else: deploys of main for those apps only, no other branches, no database dumps, no shell. One of the two is required. 

#
# we are in a laptop that already has admin
#

# ssh -t: give the session a terminal (sudo needs one to ask for the password)
ssh -t box sudo add-deploy-key --admin "PUBLIC_KEY_LINE"                        # your own laptop
ssh -t box "sudo add-deploy-key --apps 'my_app,other_app' 'PUBLIC_KEY_LINE'"    # someone else's: deploy only, those apps

#!/usr/bin/env bash
#
# file on the laptop: ~/dev/box/root/usr/local/bin/add-deploy-key
# runs on the box: boxsync installs it as /usr/local/bin/add-deploy-key
#

# add-deploy-key --admin | --apps app1,app2  PUBLIC_KEY_LINE
#   ssh -t admin@box sudo add-deploy-key --admin "$(cat ~/.ssh/id_ed25519_box.pub)"
#   ssh -t admin@box "sudo add-deploy-key --apps '*' 'ssh-ed25519 AAAA... kid-laptop-2026'"
# Appends the key to deploy's authorized_keys behind the forced command.
# --admin also appends it, unrestricted, to the calling admin's own authorized_keys.
# --apps limits the key to those apps (names, prefixes ending in *, or '*' for all), and to no dumps (see deploy-gate).
# One of the two is required: a bare key used to get every app plus dumps.
set -euo pipefail
admin=no apps=""
case ${1:-} in
  --admin) admin=yes; shift ;;
  --apps)  apps=${2:-}; shift 2
           [[ $apps =~ ^(\*|[a-z][a-z0-9_]{0,30}\*?(,[a-z][a-z0-9_]{0,30}\*?)*)$ ]] || { echo "--apps '*' (all) or 'app_one,prefix_*'" >&2; exit 2; } ;;
  *)       echo "usage: add-deploy-key --admin KEY | --apps 'a,b_*' KEY" >&2; exit 2 ;;
esac
key="$*"
# One line, ed25519 only, and a comment naming the laptop. The strict match also
# stops a crafted "key" from smuggling in a second, unrestricted line.
[[ $key =~ ^(ssh-ed25519|sk-ssh-ed25519@openssh\.com)\ [A-Za-z0-9+/=]+\ [A-Za-z0-9._@-]+$ ]] \
  || { echo "expected: ssh-ed25519 AAAA... laptop-name   (one line, comment without spaces)" >&2; exit 2; }
ssh-keygen -lf - <<< "$key" >/dev/null || { echo "not a valid public key" >&2; exit 2; }
blob=$(cut -d' ' -f2 <<< "$key")

f=/home/deploy/.ssh/authorized_keys
gate=/usr/local/bin/deploy-gate${apps:+ \'$apps\'}
if grep -qF "$blob" "$f"; then echo "already in deploy (edit the line to change its apps)"; else
  printf 'restrict,command="%s" %s\n' "$gate" "$key" >> "$f"
  echo "added to deploy (${apps:-all apps}): $(ssh-keygen -lf - <<< "$key")"
fi
if [[ $admin == yes ]]; then
  a=/home/${SUDO_USER:?run with sudo}/.ssh/authorized_keys
  if grep -qF "$blob" "$a"; then echo "already in $SUDO_USER"; else
    printf '%s\n' "$key" >> "$a"
    echo "added to $SUDO_USER (admin)"
  fi
fi
logger -t add-deploy-key "admin=$admin apps=${apps:-all} by ${SUDO_USER:-root}: $(ssh-keygen -lf - <<< "$key")"

Revoke a laptop: Tailscale -> Machines -> Remove first, which also cuts any session it has open. Then delete its keys. A deploy-only key has one line, in deploy's authorized_keys. #

Nothing needs a restart. Be careful not to delete the key of the laptop you're typing on.

If the laptop was lost or retired, that's all. If an admin laptop may have had malware, it may have had root too (see Risks I accept), and removing its key doesn't undo that: change the admin's password, then rebuild the box from Step 1 with every secret rotated.

#!/usr/bin/env bash
#
# file on the laptop: ~/dev/box/root/usr/local/bin/app-console
# runs on the box: boxsync installs it as /usr/local/bin/app-console
#

# app-console APP                IEx in a second copy of the app (bin/APP start_iex): same code, env and database, no web server
# app-console APP eval 'CODE'      one-off code in a fresh VM, app not started
set -euo pipefail
source /usr/local/lib/box/sandbox.sh
app=${1:-}
[[ $app =~ ^[a-z][a-z0-9_]{1,30}$ && -f /etc/apps/$app.env ]] || { echo "unknown app: $app" >&2; exit 2; }
# The console copy never starts the web server and never joins Erlang
# distribution, whatever the env file says. BOX_CONSOLE=1 tells the app it is
# a console, so it can skip work only the live copy should do (job queues, cron).
pre=()
case ${2:-} in
  "")     cmd=(start_iex); pre=(/usr/bin/env -u PHX_SERVER RELEASE_DISTRIBUTION=none BOX_CONSOLE=1) ;;
  eval)   cmd=(eval "${3:?usage: app-console APP eval 'CODE'}") ;;
  *)      echo "usage: app-console APP [eval 'CODE']" >&2; exit 2 ;;
esac
logger -t app-console "${cmd[0]} on $app by ${SUDO_USER:-root}"
app_sandbox "$app"
exec systemd-run --quiet --pty --collect "${SANDBOX[@]}" "${pre[@]}" "/srv/apps/$app/current/bin/$app" "${cmd[@]}"

Not reachable through deploy-gate, so a laptop's deploy key can't open a console.

Backups and monitoring

There's no automated backup. I run ssh deploy@box dump before risky migrations and resizes, and DO's weekly whole-disk backup covers the times I forget. A dump file on a laptop is plaintext, so delete it when done. Dump and restore one database once, so you know it works. 

#
# we are in the laptop
#

# the dump streams back over SSH into a local file
ssh deploy@box dump my_app > my_app_20261111.dump

# restore it into a local Postgres to check it works
# pg_restore -d: the database to restore into
createdb my_app_restore && pg_restore --no-owner --no-acl -d my_app_restore my_app_20261111.dump

DO alerts on CPU > 80% for 10 min, memory > 90% and disk > 80%, and each hostname gets an external uptime check. Once a week I look at ssh deploy@box status from the laptop, and, on the box (ssh box), at apt list --upgradable and sudo journalctl -t deploy --since -7d | grep FAILED.

Break glass aka "Oh Crap" moments
  • - Tailscale or SSH broken: DO -> droplet -> Access -> Recovery Console, and log in as the admin with the password from the password manager.
  • - A bad sshd config: install.sh puts the old one back if sshd -t fails. I keep a second session open whenever I change ssh anyway.
  • - A bad deploy: ssh deploy@box rollback my_app. A bad migration needs a database dump to go back to.
  • - A build ran bad code: reset-build (Step 10), then rotate the app's secrets if that release was deployed.
  • - Box lost: restore a DO weekly backup. Or follow this post again from Step 1, run new-app with the same name, port and host for each app, and restore its database before the first deploy:

Security review

I had AI review the setup. This is what it found, and the steps above already have the fixes:

  • - deploy-app trusted rel/LATEST. Build code writes that file, and root used it in rm -rf/cp -a/chown -R, so any dependency of any app could get root. Now deploy-app stops unless LATEST is 12 hex characters naming a real directory with no symlinks, and each app builds as its own user.
  • - cloudflared and Tailscale never got security updates. unattended-upgrades skips third-party apt repos unless you list them, and cloudflared is the one process that handles internet traffic. Now 52box lists both, and cloudflared restarts when its binary gets replaced.
  • - The deploy user owned its own home. authorized_keys belonged to root, but the directories above it didn't, so a shell as deploy could swap .ssh for its own and get rid of the forced command. Now root owns everything in /home/deploy.
  • - Root services nobody uses were running. snapd, udisks2, ModemManager, PackageKit, fwupd and bolt answer to any local user, so a compromised app could talk to all of them, and a bug in any one of them is a way to root that skips the sandbox. Step 3 removes them.
Risks I accept
  • - Cloudflare terminates TLS and sees all traffic. Whoever holds the Cloudflare account can also point a hostname at any port on the box's loopback, Postgres and sshd included.
  • - Malware on an admin laptop gets root. The admin key is a passphrase-protected file, and the admin's home on the box is writable by the admin, so the malware only has to wait for the next sudo.
  • - A bad dependency in app X can take over app X, but not the other apps.
  • - Anyone who can push to main of X's repo can run code as X's build user, and what that code leaves in the build home lasts until reset-build.
  • - Anyone who can push to the box repo is root on the box the next time I run boxsync, since it installs whatever is on origin/main as root. So push access to that repo is root access, keep that list short.
  • - A compromised app can listen on another app's port while that app restarts. Each unit could be pinned to its own port with SocketBindAllow, and I chose not to.
  • - Apps on the box can send each other requests with a forged CF-Connecting-IP, so a per-IP rate limit only holds against the outside.
  • - Nothing filters outbound traffic, so a compromised app can connect anywhere.
  • - One app can fill the disk or use all the CPU and take the others down with it.
  • - A deploy key for every app can read every app's logs.
  • - If you log into DO with your GitHub account, that one account holds the code, DO and root on the box.
  • - The biggest real risk is the accounts: DO, GitHub, Cloudflare, whatever logs into Tailscale.
Conclusion

After all of this, your applications should be up on one box, each one isolated from the others, in a fairly safe environment: no ports open to the internet, and one command to deploy from any laptop.

General Drawbacks
  • - Local Postgres -> The database runs on the same box as every app, so they all share the same 2 vCPUs, 4 GB of memory and disk. Even though we use Elixir, if we are dealing with a lot of requests we would likely struggle, or maybe not. I haven't put real load on it yet. So, do this for low traffic apps. If you need anything more than this, move the app to Fly. They have a decent intro plan now for databases that is sufficient for a legit deploy.
